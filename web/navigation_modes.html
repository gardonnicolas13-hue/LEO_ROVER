Navigation Modes

LEO Rover estimates its pose using one of two interchangeable estimators, switchable live from the cockpit without a discontinuity in the published pose (see the SE(3) correction note below).

MODE A

VINS — Visual-Inertial Navigation System

Vision-first: fuses one stereo camera pair with one IMU. Fast to converge, accurate short-term, but has no independent way to correct drift once visual tracking degrades (low light, blank walls, occlusion).

  • Camera — Intel RealSense D455 (stereo IR, infra1/infra2)
  • IMU — onboard mainboard IMU, spike-filtered (imu_sanitizer.py)
  • Estimator — MSCKF (Multi-State Constraint Kalman Filter), OpenVINS (ov_msckf)

Output — geometry_msgs/PoseWithCovarianceStamped on /ov_msckf/poseimu

MODE B

MINS — Multisensor-aided Inertial Navigation System

Fusion-first: combines every available sensor into one filter, so no single sensor's failure stops the estimate. Slower to fully converge (more states to initialize) but far more robust once running.

  • IMU — same sanitized onboard IMU stream as VINS Active
  • Wheel encoders — differential-drive velocity constraint (real radius/separation from firmware) Active
  • Camera — same D455 stereo pair, feeds visual feature tracks Active
  • Carolus (VICON slot) — beacon fix used as a drift-free global anchor, the platform's "indoor GPS" Staged, not yet enabled
  • LiDAR — RPLidar, planned integration (bring-up not yet complete) Staged, not yet enabled
  • GPS — supported by MINS, disabled on this platform (no GNSS receiver on LEO Rover) Disabled (no hardware)

Output — nav_msgs/Odometry on /mins/imu/odom

Comparison

Criteria VINS MINS
Precision High short-term (D455 calibrated to 0.20–0.23px reprojection error); drifts unbounded once visual tracking is lost. Slightly lower short-term (more states to estimate) but bounded long-term — wheel + Carolus anchor the drift.
Robustness Single point of failure: camera occlusion or low light stalls the whole estimate. Graceful degradation — losing one sensor (camera, wheel) still leaves usable state from the others.
CPU load Lower — one estimator, fewer sensor callbacks. Higher — more sensors, more states, more update steps per cycle.
Ideal use Short, well-lit, feature-rich runs; quick calibration checks; when CPU headroom is tight. Longer missions, variable lighting, whenever wheel odometry or Carolus beacons are available.

Switching live

The Pose Source button in Operations → Commands calls /pose_selector/set_source (std_srvs/SetBool) through leo_backend.py. pose_selector.py republishes a single continuous pose on /robot_pose_fused regardless of which estimator is active, applying a one-time rigid (SE(3)) correction at the exact instant of the switch so the output is bit-for-bit identical immediately before and after — no jump, even though the two estimators drift independently afterward.
