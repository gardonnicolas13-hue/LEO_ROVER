// 01 — purpose and scope

What this document is for

MINS — Multisensor-aided Inertial Navigation System (Lee et al., RPNG) — is the state estimator that fuses this rover's IMU, stereo IR cameras and wheel encoders into a single pose estimate. This page records how its parameters were set on this platform, and why.

It is written for someone who has to change a value and needs to know what will happen. Every number below is either a measurement taken on this rover, a value read from the firmware or a calibration tool, or a placeholder still waiting to be replaced — and each is labelled as such, because the three categories carry very different permission to edit.

Where MINS sits in the stack

MINS runs on the ground workstation, not on the robot. It subscribes to sensor topics republished from the Pi and publishes /mins/imu/odom. pose_selector then republishes the selected estimator onto /robot_pose_fused, which is what the cockpit and the navigation nodes consume. Three estimators can occupy that slot — MINS, openVINS, sqrtVINS — and the cockpit's Pose Source control switches between them.

That split matters for tuning: MINS costs roughly 85 % of one i7-8700 core, and the Raspberry Pi 4B is a measured 4.05× slower per core. Running it onboard is not currently viable, so every parameter here is tuned against workstation-class compute with a WiFi hop in the sensor path.

What makes this platform specific

  • It is a skid-steer rover that pivots a great deal. Four rigid wheels, no steering. During an in-place pivot the wheels scrub rather than roll, and visual landmark depth becomes unobservable. Both facts drive parameter choices that would be wrong on a car-like or aerial platform.
  • The IMU is low-grade and occasionally pathological. The CORE2's inertial unit emits rare single-sample glitches — magnitudes up to 5×1016 m/s² — which will destroy any inertial filter that sees them.
  • The camera is the only sensor constraining z. Wheels hold x and y; nothing else holds height. A camera extrinsic error has driven z to −25.9 m while x/y stayed perfect, with no alarm of any kind.
  • Sensors reach the estimator over WiFi. That constrains which topics may be subscribed and at what rate — see trap 2 below.

// 02 — prerequisites

Check the platform before you touch the filter

Tuning a filter on a sick platform produces parameters that encode the sickness. Check all of the following before changing a single value.

Battery first, always

Read /firmware/battery before anything else. This project's own threshold is 10.3 V (leo_backend.py:500), and the recorded history shows that 10.3 V already caused loss of traction (roller stall, 2026-07-10). On 2026-09-02 the pack measured a stable 9.34–9.41 V — nearly a volt below a level that had already failed — during an investigation into why the rover would not move.

A drained pack produces symptoms that look exactly like estimator or software faults: no motion, pwm_duty_cycle: [0,0,0,0], telemetry still flowing normally because it draws almost no current. Several sessions of software audit (GPIO, rosserial, checksums) found nothing, because the cause was not software. One command costs less than a day of debugging.

Pre-flight checks

CheckCommandExpected

The SCHED_FIFO 25 check is not cosmetic. Without it the serial node loses UART FIFO bytes to CPU starvation and wheel odometry collapses from ~19 Hz to ~1 Hz — which the filter experiences as a wheel sensor that has effectively stopped, and which is very easy to mistake for a tuning problem.

The two silent traps in the data path

Trap 1 — wheel messages that arrive but are never used

MINS reads wheel velocities by index (velocity[0], velocity[1]), assuming front-left and front-right. This rover's /joint_states orders them [FL, RL, FR, RR] — so index 1 is the rear left. wheel_remap.py looks the two front wheels up by name and republishes them in the order MINS assumes, on /joint_states_mins.

Worse, ROSSubscriber::callback_wheel (ROSSubscriber.cpp:165) discards every message whose name[0] is not in the sub_topics list, which defaults (OptionsWheel.h:48) to generic names this rover does not use. Without the correct sub_topics, messages arrive — rostopic hz shows them — and MINS's internal wheel stack stays at zero forever. It looks exactly like "not enough excitation", and is routinely mistaken for an initialization problem.

Trap 2 — subscribing the robot's raw camera topics

Never point MINS at the robot's raw /camera/... topics from the workstation. Two 848×480 raw streams at 30 Hz demand roughly 24 MB/s against a link that carries about 6 MB/s — this has been observed crashing the access point, not merely dropping frames. Use the local republish of the compressed stream (/pc/camera/...) configured in navigation_supervision.launch.

Launching

Both workspaces must be sourced. Note that mins/launch/ is empty in this tree — the launch file lives in leo_navigation:

source ~/TOUT/catkin_ws/devel/setup.bash   # leo_navigation
source ~/TOUT/mins_ws/devel/setup.bash     # mins
roslaunch leo_navigation mins.launch

Three properties of that launch file are load-bearing and should not be "cleaned up":

  • The config path goes through args=, not <param>. On ROS 1, run_subscribe.cpp only reads argv[1]; the parameter-server read sits inside a #if ROS_AVAILABLE == 2 block. Using <param> makes MINS try to open the literal string __name:=mins_subscribe.
  • respawn="true", never required="true". A single MINS abort under required tore down the entire stack including the cockpit — the operator lost the ability to drive because an estimator hiccuped. Accepted cost: on respawn MINS re-initializes at a new origin, so /robot_pose_fused shows a discontinuity. A discontinuous trajectory is recoverable; a dead cockpit mid-manoeuvre is not.
  • /tf is remapped to /tf_mins. MINS broadcasts global→imu at ~85 Hz, which would steal the imu frame from the URDF (a TF child has exactly one parent) and collide with openVINS. Its TF is visualization-only.

The parameters, and where each number came from

Every value carries a provenance label. This is the single most useful thing on this page: it tells you which numbers you are allowed to tune, and which ones encode a physical fact about the rover that tuning cannot fix.

3.1  IMU process noise — config_imu.yaml

These four values were characterised on this rover's own IMU with imu_utils. They are the filter's statement of how much it should trust inertial prediction between updates. Datasheet values would leave the filter overconfident, amplifying small residuals into large corrections — a failure that does not look like a typo, it looks like a broken estimator.

Never point MINS at /imu/data_raw

The onboard IMU emits rare single-sample glitches up to 5×1016 m/s². One is enough to destroy the filter. imu_sanitizer.py republishes a spike-free stream on /imu/data_clean; that is the only stream MINS should ever see.

Separately, the accelerometer's scale has been observed drifting over a scale of weeks. Before suspecting extrinsics or gyro calibration for a new drift, measure |a| at rest and compare against local gravity.

What dynamic_cloning actually does

SystemManager::dynamic_cloning() walks the available clone rates from lowest to highest and returns the first one whose predicted interpolation error falls under both intr_error_ori_thr and intr_error_pos_thr, using the calibrated slope tables (intr_ori / intr_pos, Hz_4 through Hz_30) at the bottom of the config.

So it is an accuracy mechanism whose side effect is efficiency, not an arbitrary throttle. Disabling it and pinning clone_freq: 30 — as the upstream Robomaster_S1 profile does — removes the guarantee that interpolation error stays bounded. That profile can afford it because it is also mono, downsampled, and has online calibration off. Parameters must be transplanted between profiles as a set, or not at all.

3.3  Wheel odometry — config_wheel.yaml

This is where the rover's skid-steer nature is encoded, and where the most counter-intuitive tuning lives.

The noise_w / noise_v pair deserves emphasis because the asymmetry looks like a mistake and is not. The rover's wheels are excellent at measuring distance and useless at measuring rotation. The tuning says exactly that: loosen yaw confidence hard, tighten linear confidence. A symmetric setting will either let slip corrupt heading, or reject good wheel data.

Why max_slam is 0 on this rover

During an in-place pivot the baseline is zero, so landmark depth is unobservable. With SLAM features enabled, false anchors pulled the MINS heading to +0.58 rad/s while the gyro measured −0.25, and caused correct wheel measurements to be chi²-rejected. Pure MSCKF is healthy on a platform that pivots this much. Re-enable only behind a minimum-baseline excitation guard.

Rotation error in T_imu_cam is not recoverable online

An identity-rotation placeholder claims the optical axis points up along IMU-z — a ~90° error. Observed consequence: a monotone +1.68 mm/s divergence in z that online calibration could not recover from. Centimetre-level translation error is refinable with do_calib_ext: true; 90° of rotation is not.

Because the camera is the only sensor constraining height, always check z after any change to camera geometry. A bad extrinsic has driven z to −25.9 m while x and y stayed perfect, with no alarm of any kind.

3.5  Initialisation — config_init.yaml

ParameterValueRationale

The most expensive mistake on this whole page

If the rover is handled, bumped or still settling during the initialisation window, the gravity alignment locks in tilted, gravity leaks into the horizontal axes, and the doubly-integrated residual produces an accelerating drift.

Measured on this rover: 772 m/min of drift while standing still, after an initialisation disturbed by hardware work in progress. A clean restart with the platform untouched gave 0.02 m/min — a factor of roughly 3×104, from one variable. It costs one restart to rule out. Test it before re-deriving any transform.

3.6  Verbosity — config_system.yaml

Keep verbosity: 1 (DEBUG) while tuning. All of IW_Initializer's diagnostics — waiting-for-data, gravity convergence, static/dynamic init attempts — are emitted at PRINT1 and are silently filtered at verbosity 2. At level 2, an initializer that is working perfectly and one that is doing nothing look identical.

// 04 — calibration procedure

How to bring it up, and how to prove it works

4.1  The enable ladder

Do not turn everything on at once. An unvalidated extrinsic on one sensor makes the whole fused estimate diverge and makes the divergence undiagnosable, because you cannot tell which sensor caused it. Each stage has its own enable flag.

StageSensorsPurposeRisk
1camera + IMUThe VINS-equivalent core. Prove this first.Extrinsic rotation
2+ wheelLarge gain on a ground robot.Low, once names and frame are right
3+ Carolus beaconGlobal anchor; kills accumulated drift.Beacon coverage
4+ LiDARNew integration.Treat as its own mini-project

4.2  Validation gates

These are the acceptance criteria already defined in the project's test plan. Use the blue rectangle as ground truth for the closed-loop tests.

Pass criteria
  • Static drift (60 s, stationary): position within 2–3 cm of origin, attitude within 1–2°, for the whole window. A slow monotone drift in one axis points to gravity misalignment, not to noise tuning.
  • Straight line (1 m): error under 5 %.
  • Rotation (10 turns): error under 5 % of 10×2π rad. This test is the most sensitive to a bad T_imu_cam rotation. A large error here alongside a small error on the straight line almost always means the extrinsic's rotation is off even though its translation is fine.
  • Closed rectangle: start-to-end gap under 10 cm.
  • Timing: per-frame processing under the camera frame period, with margin.
Wait for convergence before measuring anything

MINS passes through a post-initialisation transient in which drift reads at 1.7–2.5 m/min before settling to 0.001–0.006 m/min. Measuring during that window has twice produced a false verdict on this project. Allow roughly 25 seconds after initialisation, then measure.

4.3  Which parameter to touch, by symptom

Diagnose in this order. It is ordered by cost to test, not by intellectual interest — the cheap causes are also the most frequently implicated.

4.4  Validating a change

Record with rosbag rather than through the web cockpit for any run that matters: the cockpit's buffer is cleared on restarts and the websocket can desynchronise on /robot_pose_fused, neither of which is visible while it happens. Overlay the estimator against wheel odometry and the beacon on the same plot; the closed-loop gap on the blue rectangle is the headline metric.

Change one parameter at a time, and repeat each run

A single run is not evidence. On the sister estimator, an identical configuration produced a 5× difference in mean feature count between respawns — which had previously been read as seven hypotheses being "refuted", one run each. Require two consecutive passes before accepting a change.

// 05 — troubleshooting

When it is not a tuning problem

The general rule that has held throughout this project: an estimator that goes unstable immediately is almost never mistuned. Slow drift is a tuning question. Instant divergence is a configuration, calibration, or hardware question.

5.1  Power collapse masquerading as an estimator fault

Brownout is not a filter problem

When the battery falls below the 10.3 V threshold, the CORE2's behaviour degrades in ways that look like software faults. The measured picture on 2026-09-02, at 9.37 V:

  • pwm_duty_cycle: [0,0,0,0] — no actuation, no motion.
  • Telemetry continued flowing normally — wheel states at 20.1 Hz, IMU at 87 Hz — because telemetry draws almost no current. Healthy telemetry is not evidence of a healthy power rail.
  • /cmd_vel reported Subscribers: None: the CORE2's rosserial subscription was not registered at all, alongside 261 checksum errors in two minutes.

An honest caveat: the chain brownout → failed rosserial negotiation → no subscriber → no motion is plausible and consistent with everything observed, but it has not been demonstrated. The test that settles it: recharge, then re-check /cmd_vel. If Subscribers: None persists at full voltage, it is a separate fault and must be diagnosed on its own terms. Do not carry the assumption forward as fact.

The practical consequence for anyone tuning MINS: if wheel odometry degrades or disappears mid-session, read the battery before touching noise_v, chi2_mult, or anything else. A filter cannot be tuned to compensate for a sensor that has stopped reporting.

5.3  A note on editing these files

The configs are parsed by OpenCV's FileStorage, not a standard YAML parser — hence the %YAML:1.0 first line. They will fail in PyYAML, and long inline comments have broken parsing before. Validate after every edit:

python3 -c "import cv2,sys; fs=cv2.FileStorage(sys.argv[1],0); print(fs.isOpened())" <file>

When to send it

When someone reports an estimator that goes unstable immediately rather than drifting slowly. That symptom is almost never a defect in MINS — it is a configuration or calibration mismatch, and a line-by-line diff against files that are known to run resolves it fastest.
