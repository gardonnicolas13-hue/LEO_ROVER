// system reference · read this first

How the whole thing works

Every physical part, every piece of software, every word of jargon, and the paths a measurement and a command actually take. Written for someone who has never seen this platform: nothing below assumes prior knowledge of the project or of ROS.

// part 1 — the question everyone gets wrong first

Two computers, not one

Almost every misunderstanding on this platform traces back to a single question: which of the two computers is doing this? The rover carries a Raspberry Pi that talks to the hardware. A separate workstation runs the heavy estimation and serves the cockpit. They are joined by one Wi-Fi link. A node is a running program; if you do not know which machine a node lives on, you cannot reason about what happens when the link drops.

Node names are exactly what rosnode list returns on the running system; each was mapped to its machine by querying its own XML-RPC address, not assumed from a launch file. Note the asymmetry: the rover runs drivers, the workstation runs everything that thinks.

Why this split matters in practice

The ROS master — the directory that lets programs find each other — runs on the rover. When the Wi-Fi drops, workstation programs keep running but lose their registrations, so they look alive to every simple health check while producing nothing. That single fact explains a large share of this project's hardest debugging sessions.

// part 2 — the outbound path

From a wheel tick to a dot on your screen

Four physical sources feed the position estimate. Each is cleaned before it reaches an estimator — never after, because filtering an estimator's output instead of its input is how this project once turned a filter into the fault. Two estimators run the same data in parallel and a selector decides which one the rest of the system believes.

Every box is a real running program and every topic name is the real one. The dashed red band is the point most people miss: driving the rover by hand uses none of the estimation chain, which is why manual control can work perfectly while the position display is frozen — and why the reverse is also possible.

// part 3 — the wiring

The topics that carry everything

In ROS, programs never call each other directly. They publish messages on named channels called topics, and anyone interested subscribes. This is why a program can be perfectly alive and still useless: it is registered, but nothing is flowing. Message types below are exactly what rostopic type returns on the running system.
